# /ship — 보고서 · 퀴즈 · 커밋 제안

인지부채 대응 워크플로다. diff 를 그대로 던지지 않고, 사용자가 변경의 그림을
능동적으로 복구하게 만든 뒤 커밋한다.

## 1. 변경 파악

- `git status` / `git diff` (+ 신규 파일 내용) 로 미커밋 변경 전체를 파악한다.
- 인자로 범위가 주어지면 그 범위만 다룬다.
- 변경을 **주제(기능) 단위로 묶는다** — 이 묶음이 보고서 섹션이자 커밋 단위가 된다.

## 2. 보고서

- `docs/worklog/YYYY-MM-DD-<slug>.md` 에 작성. 주제별로:
  - 무엇이 왜 바뀌었나 (2~4문장)
  - **부작용 가능 지점** — 이 변경이 물릴 수 있는 곳, 영향받는 테이블/라우트/화면
  - 수동 확인 포인트 — 직접 눌러보면 좋은 곳
- 짧게 쓴다. 읽는 부담이 이 워크플로의 실패 원인이다.
- 구조나 데이터 흐름이 바뀐 큰 변경이면 다이어그램을 곁들인다.

## 3. 이해도 퀴즈 (소프트 게이트)

- **문항 수는 최소 5문제.** 변경의 규모와 위험도에 따라 그 이상으로 늘린다.
  사소한 변경(오타/스타일/설정)만 있을 때는 퀴즈를 생략하고 4번으로 간다.
- AskUserQuestion 으로 선택지형으로 낸다. 한 번에 최대 4문항이므로
  5문항 이상은 여러 번에 나눠 낸다.
- **문제 원칙: 트리비아 금지.** 나중에 실제로 물릴 지점만 묻는다:
  - "이 변경 후 X 상황이 되면 무슨 일이 일어나나"
  - "이 코드가 건드리는 테이블/라우트/화면은 어디까지인가"
  - "잘못되면 어떻게 되돌리나 (롤백 경로)"
  - "이 경계값/예외 케이스에서의 동작은"
- 오답이 나오면 그 지점을 해설한다. **오답 지점이 이 워크플로의 수확이다** —
  그림이 안 그려져 있던 곳을 찾은 것이니, 그 부분의 동작을 다시 설명한다.
- 사용자가 건너뛰길 원하면 건너뛴다 (강제 게이트가 아니다).

## 4. 커밋 제안

- 주제 단위로 커밋 계획을 제시한다: 커밋별 파일 목록 + 메시지 초안.
- worklog 파일도 커밋에 포함한다.
- **승인받은 뒤에만 커밋한다.** (AGENTS.md 커밋 규칙 그대로)
- 푸시는 별도 요청이 있을 때만.
