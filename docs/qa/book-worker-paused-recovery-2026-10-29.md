# 교재 Batch 중지와 저장 응답 복구

## 운영 조치

- 사용자의 추가 비용 중지 요청에 따라 `edunote-book-batch` Cloud Tasks 큐를 PAUSED로 변경했다. 이 큐는 은행 Batch의 자동 재개를 공유한다.
- 실행 중이던 `edunote-bank-pdf-6sv5d`, `edunote-bank-pdf-bnzks`를 취소했다. 실행 종료를 확인했다.
- 네 작업을 failed 상태로 고정하고 stage에 `사용자 요청으로 자동 처리 중지 · 기존 응답 보존`을 표시했다. lease와 resume_after는 해제했다. PDF·문항·기존 체크포인트는 삭제하지 않았다.
- 은행 워커에 `PDF_IMPORT_CACHE_ONLY=true` 설정을 준비하고 Anthropic secret binding을 해제했다. 기존 배포 바이너리는 cache-only 옵션을 모르므로 binding 해제가 현재의 추가 방어다. Secret Manager 키 자체는 삭제하지 않았다. 주차 워커는 변경하지 않았다.
- 재개 시에도 승인 전 자동 처리·생성을 켜지 않는다. 향후 은행 워커 키 연결 복원 값은 `ANTHROPIC_API_KEY=edunote-anthropic-api-key:1`이다. 이 문서에는 키 값이 없다.

## 이미 접수된 요청

- `msgbatch_01NSDkovoyZPTB5zstg8huyY`: 55개 성공, 취소 확인 당시 이미 ended.
- `msgbatch_01TUPoo8wK6j5SvhVHAP7XDK`: 80개 처리 중인 상태에서 취소 접수. 이후 ended, 80개 성공·취소 0으로 확정됐다.
- 따라서 이미 접수된 135개 요청의 비용을 취소·환불했다고 볼 수 없다. 이번 작업에서 새 생성·배치 접수는 하지 않았다.
- 두 배치의 응답 custom_id·모델·개수와 기존 요청 메타데이터를 대조했다. 기존 전송 형식과 동일한 `batch-result:<key>` 체크포인트로 135개 응답을 추가 보존하고, 원래 batch ledger를 ended로 갱신했다. 작업의 중지 상태는 유지했다.
- 원문 응답과 진단 스냅샷은 ignored `tmp/pdfs/`에 있다. 생성 키는 메모리에서만 사용했고 파일에 기록하지 않았다.

## 원인과 수정

- 기존 layout-v1 워커와 최근 학년도 수정 배포본의 원문 체크포인트 키·매핑 응답 형식이 달랐다. 기존 8개 검증 원문의 키는 `layout:1`을 포함하는 키와 모두 일치했다. 최근 배포본은 그 필드와 응답의 layout_version/breaks를 처리하지 못했다.
- 두 키를 순서대로 확인하되 원본 PDF 해시·문항 manifest 해시·추출 해시·이미지 대조 proof·validation을 모두 통과한 원문만 재사용한다.
- 매핑·대조·부분 복구 요청은 배포 당시의 정확한 프롬프트 버전도 조회한다. PDF와 좌표 증거를 포함하는 전체 요청 키가 같은 응답만 재사용한다. 번호만 같다는 이유로 응답을 연결하지 않는다.
- layout-v1 응답의 문단 경계를 보존한다. label의 줄바꿈 누락은 본문 누락으로 간주하지 않으며, 본문의 미지정 경계는 계속 차단한다.
- Wingdings 사각형 U+F06F를 목록 기호로 인식한다. 어휘에 배정된 나머지 글자가 확인된 경우만 선행 기호 누락을 처리한다. 영어 첫 글자나 본문 속 기호는 임의로 제외하지 않는다.
- 같은 출처표기의 label/section_label 중복 주석과 목록 기호 중복 주석을 구분한다. 본문·해석·해설의 중복은 계속 차단한다.
- 검증 응답에 target과 정확히 같은 주소가 중복 출력된 경우만 중복 속성을 제거한다. 주소 충돌·미지의 속성은 계속 오류다. repair를 pass로 바꾸지 않는다.
- cache-only 복구에서는 저장 응답을 읽을 수 있지만 새 배치 수집·접수, 직접 생성·예열을 차단한다. 기존 품질 복구 한도를 올리지 않았다.

## 검증과 한계

- 네트워크 fetch를 차단한 로컬 재생으로 기존 8개 원문과 보완 응답을 재사용했다. 8개 모두 최종 bookProofMatches 통과, 새 요청 0이다. 운영 문항으로 게시하지 않았다.
- 점검 당시 보류된 21개 묶음 모두 기존 매핑 응답 중 수정된 구조 검사를 통과하는 후보가 있었다. 이는 내용 정확도나 이미지 대조 완료를 뜻하지 않는다. 후보가 바뀌면 해당 후보에 대한 유효한 기존 이미지 대조 응답이 필요하다.
- 다른 운영체제에서 다시 만든 PDF/이미지/좌표나 다른 후보로 요청 키가 달라지면 기존 응답을 임의 연결하지 않는다. 최초 로컬 매핑 재생에서 중단됐던 구간은 이후 과거 프롬프트 문자열의 CRLF/LF 불일치로 확인했다. JavaScript template literal의 실제 LF 값을 복원하자 같은 구간이 저장된 layout-v1 응답을 정확한 요청 키로 재사용했고 구조 오류 0·새 요청 0으로 통과했다.
- `npm run check -- --maxWorkers=2`: 189개 파일, 1,635개 테스트 통과. 타입·린트 오류 0, 기존 린트 경고 21개 유지.
- `npm run build:worker` 및 `git diff --check` 통과.
- 수정 소스는 로컬에 있으며 이번 요청에서는 커밋·푸시·워커 이미지 빌드/배포·Vercel 배포·작업 재개를 하지 않았다. 운영은 중지 조치와 응답 보존만 반영했다.

### SQL 적용과 운영 상태

`supabase/migrations/20261029113902_book_pdf_cost_controls.sql`을 새로 만들었다. 새 원문/문항을 만들지 않으며, 예산/예약 테이블·비용 tier·서버 전용 RPC를 추가한다. 과거 사용량은 기존 체크포인트를 읽어 예산에 반영하고 기존 작업에 확인 필요 상태를 설정한다. 예산을 모르는 구버전 워커의 교재 접수도 DB에서 거절한다.

AGENTS.md의 "사용자가 개발/운영 DB 양쪽 SQL Editor에 직접 붙여넣어 적용함" 규칙에 따라 이번 구현에서는 실제 DB에 적용하지 않았다. 적용 순서는 각 DB의 전체 SQL → 수정한 UI/워커 배포(작업 재개 없이) → 아래 환경별 과거 비용 기록 채우기다. UI가 Batch 단가를 구분하기 전에 기록을 채워 일반 단가로 표시하는 것을 피한다. 반복 실행해도 같은 이벤트는 중복되지 않는다.

```sql
-- 개발 DB에서만:
select public.pdf_batch_backfill_usage('development');
-- 운영 DB에서만:
```
