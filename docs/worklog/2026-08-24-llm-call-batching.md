# 2026-08-24 — LLM 호출 병렬화/배치화 (Tier 1) + maxDuration 실측

Vercel `maxDuration = 300` 대응 논의의 첫 단계. HTTP 구조는 안 건드리고 함수 안에서
LLM 콜만 병렬화/배치화했다. 전후를 실제 과금 호출로 실측해 유익한 것만 남겼다.

## 1. AI 해설 생성 배치화 — 사실상 버그 수정

`generateExplanations` 가 18~45번(27~28문항)을 **opus 1콜**(maxTokens 16000)에 넣던 것을
내부에서 **7문항 배치 × 동시 4**로 분할 ([exam-bank.ts](../../src/lib/llm/exam-bank.ts)).
시그니처는 opts 파라미터 추가 외 불변이라 호출부 수정 없음.

**실측 (개발 DB 기출 27문항, 동일 세트)**

| | OLD 단일 콜 | NEW 7×동시4 |
|---|---|---|
| 시간 | 280.9s (300s 천장 스침) | **134.6s** |
| 반환 | **11/27** — 출력이 maxTokens에 잘려 30~45번 유실, 폴백 파서가 건진 것만 생존 | **27/27** |
| 총 출력 | 10,562자 | 28,382자 |

즉 기존 운영에서 「AI 해설 생성」을 쓸 때마다 **뒷번호 해설이 조용히 누락되고 있었을
가능성이 높다.** 속도 개선이 아니라 유실 버그 제거가 본질.

**부작용 가능 지점**
- 배치 하나라도 실패하면 전체 throw — 기존 단일 콜 실패와 같은 의미라 라우트 동작 불변.
  단, 성공한 배치의 결과도 버려진다 (기존과 동일하게 클라이언트가 전체 재시도).
- `reading-explanations.ts` 는 자체적으로 6문항 배치를 만들어 호출 — 6 < 7 이라
  내부에서 단일 배치로 통과, 이중 분할 없음.
- 영향 라우트: `exam-bank/[id]/generate-explanation`, `weeks/[id]/import-problem-answer-key`
  (해설 자동 생성 경유).

## 2. OMR·답안지 OCR 동시화 (1 → 3)

[mock-exam.ts](../../src/lib/llm/mock-exam.ts) `ocrExamAnswerBatch` / `ocrExamOmrBatch` 에
`concurrency: 3`. 페이지가 서로 독립이고 `mapWithConcurrency` 가 결과를 입력 순서로
돌려주므로 `page_number` 부여·병합 순서 불변. 저빈도 기능이라 실측은 생략.

**부작용 가능 지점**: 장수 많은 OMR 업로드 시 분당 토큰(TPM) 소모가 3배로 몰림 —
다른 LLM 작업과 동시 실행하면 서로 느려질 수 있음.

## 3. 문제지형 파싱 동시 2→3 — 실측 후 되돌림

44p 내신 PDF(청크 11)로 실측: **동시 2 = 641.8s, 동시 3 = 669.8s.** 동시성을 올린 만큼
콜당 시간이 늘어(107s→167s) 벽시계 이득이 없었다 — **TPM 한도가 병목**이라 병렬은
같은 토큰 예산을 나눠 쓸 뿐. `PDF_PARSE_CONCURRENCY = 2` 유지, 실측 근거를 주석으로 남김
([week-reading-import.ts](../../src/lib/week-reading-import.ts)).

두 동시성 런의 문항 수(157)·번호가 완전 일치 — 동시성이 파싱 결과에 영향 없음도 확인.

## 4. 실측이 알려준 것 (다음 단계 근거)

- 용산고 44p 전체: 641s — **300s 안에 절대 불가**. 영어만(1~11p): 152.5s (청크 125/131/26s) — 통과.
- 40문항 내외 내신(13~15p, 청크 4~5)이면 250~330s — **경계선 복불복.**
- 청크당 최대 ~131s ≤ 300s → **청크당 요청 분리(Tier 2: 클라 오케스트레이션 + 스테이징
  + finalize)가 다음 단계.** TPM 병목이라 병렬 확대는 답이 아님을 실측이 확정.
