# 2026-08-26 — 기출은행 파싱 청킹 전환 + 수제 폴백 제거

## 무엇이 왜

기출은행 PDF 업로드(`POST /api/exam-bank`)가 문서 통째(whole) 1회 파싱 + 라우트 수제
try/catch 폴백("필터에 걸리면 전체를 페이지 단위로 재파싱")이던 것을, 파이프라인 엔진의
표준 스펙 선언으로 교체했다.

```
전:  whole 1청크 순차 → 필터 시 전체 페이지 재파싱 (2배 과금)
후:  경계 정렬 3p 청킹 × 동시 4 → 실패 청크만 페이지 재시도, 필터는 즉시 skip
```

- **속도**: whole 은 concurrency 설정이 무의미(완전 순차)했다. 10p급 기출이 대략 청크 1개
  시간으로 떨어진다.
- **잘림 위험 제거**: 45문항 JSON 을 maxTokens 32768 응답 1개에 받던 구조는
  "27문항 해설 중 11개 생존" 사고와 같은 실패 형태 — 청크당 출력이 1/3 로 줄어 구조적으로 해소.
- **필터 비용**: 걸린 청크만 페이지 재시도. 전체 재파싱(2배 과금) 없음.
- 41~45 장문 세트가 청크 경계에 걸리는 경우는 2겹 방어:
  ① `alignToQuestionStart` — 다음 페이지가 문항으로 시작할 때만 자름 (최대 5p까지 밀기)
  ② `propagateSharedPassage` 후처리 — 지문이 비고 발문이 "윗글의…"면 직전 지문 복사
- 번호 재배정(`renumberDuplicateQuestions`)은 **일부러 제외** — 기출 번호(18~45)는 통계
  매칭·해설 생성의 키라 재배정이 오염이 된다. 병합 후 중복 번호는 로그로만 감지.

## 부작용 가능 지점

- `skipped_pages` 응답 의미 변화: 전에는 "페이지 폴백 모드의 청크 순번(=페이지)"만 채워졌고
  평시엔 빈 배열. 이제 엔진 skip 범위(청크 skip + 페이지 skip)에서 계산한 원본 기준 페이지
  번호. 클라(exam-bank 페이지)의 결손 표시 UI가 이 필드를 읽는다면 표시 빈도가 늘 수 있다.
- 청크 병렬(동시 4)이라 Anthropic rate limit 소모 속도가 빨라진다. 다른 파싱과 동시 실행 시
  429 가능성 — SDK 기본 재시도 2회에 맡김.
- 이미지 업로드(mimeType ≠ PDF)는 splitFile 이 as-is 1청크로 돌려 whole 과 동일 동작.
  필터에 걸리면 skip → 0문항 → 기존과 같은 422 + exam 행 삭제 경로.
- 스캔형 PDF(텍스트 추출 불가)는 경계 정렬이 폴백으로 기계적 3p 컷 — 지문 분리 확률이
  올라가지만 ②지문 전파가 받친다.

## 수동 확인 포인트

- 실제 기출 PDF 1회 업로드(과금): 문항 수가 기존과 동일한지, 41~45번 passage 가
  비어 있지 않은지, `skipped_pages` 가 평시 빈 배열인지.
- 콘텐츠 필터에 걸리던 회차가 있으면 그 파일로: 걸린 페이지만 빠지고 나머지가 저장되는지.
