# 2026-08-27 — 주차 가져오기 통합: 출력 범위 분할 + 분리형 제거 (−2,015줄)

## 무엇이 왜

주차 시험 자료 업로드를 **통합 PDF 1개 → 번호 발견 → 범위 병렬 파싱** 단일 흐름으로 통일하고,
분리형(문제지형/정오표) 업로드와 그 기반이던 청킹·스테이징 장치를 전부 제거했다.
근거: 중간/기말(분리형의 존재 이유)은 실사용이 거의 없고, 해설지형 통합 문서가 대부분이라는
운영 판단 + 범위 분할이 통합형 실측(숭문 7p, 84s, 소문항 분리·정답 원문 일치)을 통과함.

```
업로드 카드: PDF 1개만 (문항/해설·정오표가 따로면 사용자가 합쳐서 업로드)
  → 임시 스토리지 → parse-answers 1요청
     번호 발견 콜(캐시 예열 겸, 출력 ~수십 토큰) → 번호 6개씩 그룹 병렬 → 병합·저장
  → 해설 드레인 (기존 유지)
  실패 시: 통짜 1콜 폴백
```

## 구조 변화

- **`llm/ranged.ts` 신설** — 출력 범위 분할 코어를 도메인 공용으로 승격:
  `rangedParseCall`(range/numbers 스코프) · `prewarmPdfCache` · **`discoverQuestionNumbers`**
  (번호 미지 문서용 — 파싱 대신 번호 목록만 출력받아 캐시 예열을 겸함) · `sliceNumbers` ·
  `filterByScope`(범위 지시 위반 안전망). 기출은행도 이 코어를 탄다.
- **`parseAnswerSheetRanged`** (week.ts) — 번호 발견 → 그룹 병렬, 필터 걸린 그룹만 skip
  (결손 번호는 응답 `skipped_questions` 로 보고 → 업로더 토스트 안내).
- **삭제 (−2,015줄)**: 라우트 7개(`import-plan/chunk/finalize`, `answer-key-chunk/finalize`,
  `import-problem-sheet`, `import-problem-answer-key`), 문제지형 청킹 파이프라인·스테이징 함수군,
  경계 분할, 백지 슬라이스 폴백, 문서 유형 감지, 정오표 파서·프롬프트, 업로더의 모드 분기·
  2문서 오케스트레이션·이미지→PDF 변환·파일 순서 UI (1,078줄 → ~400줄).
- 프롬프트: "앞쪽 시험지부 + 뒤쪽 해설부 합본이면 번호로 조합" 규칙 — 사용자가 병합해 올린
  PDF가 정확히 이 형태다. `source_page` 는 단일 문서 페이지 번호로 회귀.

## 부작용 가능 지점

- **기능 축소 (의도됨)**: 이미지 업로드 불가(PDF만), 정오표-나중-반영 흐름 없음 —
  정답만 갱신하려면 통합 PDF 재업로드(재채점 경고 다이얼로그 경유)가 대체 경로.
- 대용량 PDF: 업로더가 항상 임시 스토리지(`import-upload-url`) 경유 — 4.5MB body 한도 무관.
- `exam-pdf-temp` 버킷 JSON 허용 마이그레이션(스테이징용)은 용도 소멸 — 롤백 불필요, 방치.
- 통합 흐름의 실 LLM 검증은 통합형 1파일 케이스만 완료. 첫 실사용이 사실상의 검증이고,
  실패 시 통짜 폴백이 받는다.
- upload-store 의 `AnswerSheetStatus` 사용 형태 단순화 — 다른 화면에서 이 상태를 읽는 곳이
  있다면 loading step 문구만 달라진다.
