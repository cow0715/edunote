# 해설지 파싱 규칙 정비 — 계약 재조직 · 정규화 계층 · 조용한 결손 제거

발단: 공유 리포트 다시풀기가 `choices` 가 빈 객관식(밑줄·삽입·무관한 문장 유형)을 지문에서
기호를 세는 휴리스틱으로 살리고 있었다. 추적해 보니 스키마가 아니라 **프롬프트 규칙 세 개가
서로 다른 시기에 다른 목적으로 들어와 한 호출에 합쳐지며 충돌**한 것이었다.

| 규칙 | 들어온 날 | 목적 | 문제 |
|---|---|---|---|
| 64번 "밑줄은 지문 안 번호 단어에, 별도 선지 목록엔 붙이지 말라" | 5/24 | `<u>` 마크업 **위치** | 모델이 "선지 목록을 만들지 말라"로 읽음 → 같은 발문이 런마다 채워지거나 비거나 |
| 70번 "choices 에 기호 유지" | 5/24 | 문제지형 파이프라인용, 원본이미지 블록에 잘못 위치 | 249번과 정면 충돌 |
| 249번 "choices 는 기호 없이" | 9/1 | 해설지형 조각 규칙 | 70번과 정면 충돌 |

운영 데이터로 확인: 토씨까지 같은 발문("밑줄 친 부분 중 문맥상 낱말의 쓰임…")이 용산고 9/1 에선 5선지,
서울여고 9/2 에선 null. **inline 으로 가자는 결정은 애초에 없었다** — 편차였다.

## 0. 검증 장치 — golden 하네스 (`scripts/test-parse.ts`)

프롬프트를 고정하는 테스트가 0개였고 `tests/fixtures/` 가 비어 있었다. "대대적 수정"의 최대 리스크는
범위가 아니라 이것이었다.

- 하네스가 **운영 라우트와 같은 진입점**(`parseAnswerSheetDocument`)을 탄다. 예전엔 통짜 `parseAnswerSheet` 만 불러
  실제 경로(범위 분할 → 폴백)와 달랐다.
- golden 에 채점 계약(style·정답) + **구조 조각(발문/지문/선지 유무·선지 내용)** 을 담는다. 해설 본문은 안 담는다 (매번 달라져 소음).
  선지는 파이프라인 정규화 결과를 **그대로** 담는다 — 하네스가 또 기호를 벗기면 문장 삽입 문항(`["①",…]`)이
  `["","","","",""]` 로 저장돼 diff 가 눈멀게 된다 (한 번 그렇게 저장됐다가 잡음).
- 픽스처 4개(개발 스토리지에서): 숭문 week4(17, 소문항·find_error), testweek4(28, 객관식), week8-1(24, multi_select 포함),
  예열TEST(6). **PDF 는 커밋하지 않는다** (`tests/fixtures/.gitignore`). golden 만 커밋.
- 실행은 과금이다 — 사용자 요청 시에만. `--all` 대조 / `--all --update` 갱신.
- 발견: 정적 `import` 는 `loadEnv()` 보다 먼저 실행돼 Anthropic 클라이언트가 빈 키로 만들어졌다 → 동적 import 로 순서 보장.

**빠진 커버리지**: OX/TF 문항 (운영 용산고 week1 에만 있고 로컬 스토리지엔 없음). 사용자가 해당 PDF 를
`tests/fixtures/` 에 넣고 `--update` 하면 된다.

## 1. 프롬프트 재조직 (`src/lib/prompts.ts`, `src/lib/llm/week.ts`)

- 흩어져 있던 `question_text`/조각/선지 규칙을 **"출력 필드 계약" 한 블록**으로 — 필드마다 타입·빈값·예시가 한 곳에.
- 70번 제거(원본이미지 블록에서), 64번을 마크업 위치 규칙으로만 명확화.
- **지문 내장형 선지 규칙**: 밑줄 어법/어휘 → 밑줄 표현 그대로, 무관한 문장 → 문장 전체, 문장 삽입 → 기호만(`["①",…]`).
  객관식이면 `choices` 를 **항상** 채운다. 예시 JSON 에 밑줄 어법·문장 삽입 두 건 추가 (규칙보다 예시가 세다).
- 문제지형 파서(`parseWeekProblemSheetPage` + 규칙 + 타입)와 dev 비교 라우트/컴포넌트 삭제 — 8/27 통합 가져오기로 죽은 코드였다.

**부작용 가능 지점**
- 새로 파싱되는 밑줄·삽입·무관한 문장 문항에 `choices` 가 생긴다. 소비자가 "choices 있음 = 시험지에 목록 있음" 으로
  가정하면 유령 목록이 생긴다 → 아래 2 의 조립기 규칙이 막는다.
- `question_type` 은 자유 문자열이라 런마다 표현이 흔들린다 (하네스에선 ℹ️ 참고 차이로만).

## 2. 저장 전 정규화 계층 (`src/lib/parsed-answer-normalize.ts`) — 결정적, 테스트 18케이스

LLM 출력을 컬럼에 넣기 전에 한 형태로. 프롬프트 편차는 여기서 끝난다.

- `choices`: 기호 제거 · `[]`/1개 → `null` · **객관식·multi_select 에만**(find_error 에 ⓐ~ⓔ 후보가 실려 오는 런이 있었다) ·
  기호뿐인 선지("①")는 기호를 살린다(삽입 위치).
- 빈 문자열 → `null` (undefined/null/"" 삼중 상태 제거).
- `correct_answer`: objective 외엔 0. `multi_select` 정답키 `①,③`→`1,3`, OX 는 공백만 정리.
- 조각이 다 비었고 `question_text` 에 **빈 줄 구조가 실제로 있을 때만** 분해 (줄바꿈 하나짜리 통짜는 발문 자리에 전문이 들어가므로 거부).

**조립기** (`question-structure.ts` `buildQuestionTextFromParts`): 선지가 전부 기호뿐이거나 각 선지 텍스트가 지문에
그대로 있으면(`choicesAreInline`) 목록을 붙이지 않는다 — 성적표·편집기·오답노트에 시험지에 없는 다섯 줄이 생기지 않게.
데이터로만 판정한다(추측 아님).

**다시풀기** (`reading-review.tsx`): 지문에서 기호를 세던 휴리스틱 3겹 삭제. `choices.length >= 2` 만 본다.
기호뿐인 선지는 번호 버튼 레이아웃.

## 3. 범위 분할의 조용한 결손 (`src/lib/llm/ranged.ts`, `week.ts`) — 실측으로 잡은 기존 결함

golden 대조 5회 중 2회, 발견된 번호가 결과에서 **아무 보고 없이** 빠졌다 (숭문 4번, week8-1 20번).

- 원인 ①: 결손 판정이 콘텐츠 필터 skip 에만 있었다. 모델이 범위 안 문항 하나를 빼먹으면 신호가 없다.
  → `findMissingNumbers`(발견 − 결과 − 필터결손)로 대조해 **1문항 콜 재시도**, 그래도 없으면 **결손 보고**(업로더 토스트).
- 원인 ②: 범위 콜 하나가 JSON 파싱 에러를 내면 `rangedParseCallIsolated` 가 throw → **문서 전체가 통짜 폴백** →
  통짜가 `max_tokens` 로 잘려 12/17 문항. → JSON 파싱 에러도 필터처럼 **문항 단위 격리**, 1문항 콜까지 실패하면
  throw 대신 결손. 통짜 경로는 `max_tokens` 잘림을 경고한다. 파싱 실패 시 raw 응답 앞 600자를 로그에 남긴다.
- 원인 ③ (raw 로그가 잡아냄): 그 JSON 에러의 정체는 모델이 **바깥 `[ ]` 없이 객체만** 낸 응답이었다(1문항 콜에서 발생).
  `extractJsonArrayCandidate` 가 첫 `[` 를 찾다가 지문 속 `(A) [ making / made ]` 대괄호를 잡아 엉뚱한 구간을
  잘라냈다 — 그래서 매번 정확히 `position 188`. 1번 문항(괄호 어법)에서 결정적으로 재현됐고, 격리 재시도가
  1문항 콜로 내려가도 같은 이유로 영원히 실패했다. → 응답이 `{` 로 시작하면 배열로 감싼다(`client.ts`).
  이제 `parseJsonArrayResponse` 는 항상 배열을 돌려준다 (비배열 결과도 감싼다).

**부작용 가능 지점**
- `skippedNumbers` 에 필터 외 원인(모델 누락·JSON 깨짐)이 섞인다. 업로더 토스트("N번 문항은 인식하지 못했습니다 —
  직접 추가하거나 파일을 다시 올려주세요")는 원인 중립이라 그대로 맞는다.
- 재시도가 콜 수를 늘린다 (캐시 히트라 비용은 작다). 결손이 많은 문서면 벽시계가 늘어난다.

| 항목 | 결과 |

| JSON 파싱 에러 → 통짜 폴백 → `max_tokens` 잘림 (숭문 12/17) | 격리 재시도로 **17/17 복구** |
| 22번(week8-1) | 기준선 `multi_select "2,3"` → `22a/22b`. 발문이 "(a)~(e) 중 어법상 틀린 것을 2개 고르면? ① (a) ② (b)…" 라 **STEP2 ⑥ 규칙상 분리가 맞다** (기준선·3월 저장분이 규칙 위반). 5런 중 4런 분리·1런 미분리로 흔들려서 ⑥ 에 이 형태의 예시와 "multi_select 로 내지 말 것" 을 추가 → 이후 **2런 연속 분리** |

**남은 편차 (이번 범위 밖, 다음 고정 대상)**
- `find_error` 소문항 표기: 숭문 2번이 `2|`(sub_label 없음, `"2:struggle"`) 와 `2|b` 사이를 오간다. STEP2 ⑤ 는 기호별
  sub_label 을 요구하므로 `2|b` 쪽이 규칙에 가깝다. 재업로드 매칭 키(번호|소문항)에 영향을 주므로 규칙 문장을 조여야 한다.
- 1런에서 week8-1 21번 발문이 비어 온 적 있음 (재현 안 됨).
- `question_type` 은 자유 문자열이라 런마다 표현이 다르다 — 하네스에 `tagCategories` 를 넘기지 않아서다. 태그 목록을
  넘기면 고정된다.
