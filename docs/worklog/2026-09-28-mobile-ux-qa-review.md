## 범위와 증거 구분

- **실화면 확인**: 열려 있던 운영 share 링크를 별도 QA 탭으로 열어 오답 목록 → 다시 풀기 → 선택 → 정답 확인 → 나가기, 단어장 검색, 분석 탭을 확인했다. 관리자 수업 현황·모바일 메뉴·학원 정보 설정도 조회했다.
- share 복습은 375×812, 320×640 뷰포트 설정으로 확인했다. 스크롤바 때문에 실제 콘텐츠 가용 폭은 설정값보다 작다. 관리자 화면은 기존 모바일 폭에서 확인했다.
- **코드 확인**: 로컬 작업 중 코드에서 데이터 처리·오류·재시험·설정 동작을 추적했다. 운영에는 로컬의 테마 선택 기능이 아직 보이지 않는 등 버전 차이가 있다. 배포 코드와 로컬 코드가 동일하다고 가정하지 않는다.
- **추가 검증 필요**: 실제 iOS/Android 키보드, OS 글자 확대, 브라우저 뒤로가기 제스처, 네트워크 장애, 이미지가 필요한 문항, 다크 모드.
- 실제 학생을 모집한 사용자 테스트는 아니다. 학생·학부모·강사의 과업을 따라 수행한 전문가 QA다. 전체 앱의 모든 기능을 검증한 결과도 아니다.
- 독해 복습은 코드상 서버 제출 없는 로컬 연습이라 선택·확인을 수행했다. 단어 재시험은 자동 제출 및 실제 기록 변경 가능성이 있어 진입하지 않고 코드로만 검토했다. 설정 저장·문자 발송·학생 데이터 수정은 수행하지 않았다.
- 다른 세션의 디자인 작업과 겹치지 않도록 이 문서만 추가했다. 데스크톱 설계는 제안하지 않는다.

## 판단

문제 읽기에 필요한 본문 크기·정렬·읽기 순서·스크롤 구조가 리포트의 작은 카드 규격에 묶여 있다. 학생은 문제의 요구를 파악하고 지문과 선지를 비교해야 하는데, 현재 화면에서는 작은 글씨를 읽고 긴 영역을 오가며 맥락을 기억해야 한다. 색이나 라운드의 취향보다 먼저 해결할 문제다.

P1은 학습·정보 해석을 직접 방해하는 항목, P2는 반복 사용의 부담과 접근성을 개선하는 항목으로 구분한다. 아래 제안의 글자 크기는 제품 설계 제안이며 WCAG가 요구하는 일률적 최소 폰트 크기가 아니다.

## A. 문제 다시 보기·다시 풀기

### Q01 [P1 · 실화면/코드] 작은 영문 + 양쪽 정렬 + 좁은 본문 폭

- 오답 목록은 13.5px semibold, 다시 풀기의 지문은 13px이며 모두 `text-justify`를 쓴다. 운영에서 영문 단어 사이 간격이 크게 벌어지는 줄을 확인했다.
- 오답 목록의 본문은 전체가 두꺼워 발문과 지문 사이 위계도 약하다. 바깥 여백과 카드 안 여백이 겹쳐 실제 읽기 폭이 줄어든다.
- 학생 영향: 긴 지문을 여러 줄 따라 읽을 때 시선 흐름이 끊긴다. 오답 목록과 다시 풀기의 같은 지문이 서로 다른 크기·무게로 보여 읽기 경험도 달라진다.
- 제안: 문제 본문 전용 타이포를 두어 16px 전후·보통 굵기·왼쪽 정렬·줄높이 1.65~1.8부터 검증한다. 발문은 굵게, 본문은 일반 굵기로 분리한다. 글자 크기 선택을 제공하되 지문 누락이나 클리핑 없이 적용한다.
- 근거: `wrong-answer-card.tsx:122`, `reading-review.tsx:200`.
- 합격 조건: 320/375/430px에서 영문 간격이 자연스럽고, 200% 글자 확대에서도 내용과 버튼이 잘리지 않는다.

### Q02 [P1 · 실화면/코드] 문제 질문보다 긴 지문이 먼저 나온다

- 다시 풀기는 지문 → 문제 번호·발문 → 선택지 순서다. 확인한 긴 빈칸 문제의 첫 화면 대부분은 지문이고 선택지는 화면 아래에 있다.
- 학생 영향: 무엇을 찾으며 읽어야 하는지 모른 채 읽기 시작하거나, 질문을 확인한 뒤 다시 위로 올라간다.
- 제안: 문항 번호·출처 회차 → 발문 → 지문 → 선택지 순서로 통일한다. 스크롤 후에는 필요할 때 발문/지문 위치로 돌아갈 수 있는 간단한 이동 수단을 검토한다.
- 근거: `reading-review.tsx:199–214`.
- 합격 조건: 첫 진입 화면에서 문제의 요구를 바로 알 수 있다.

### Q03 [P1 · 실화면/코드] 선택지 번호 중복

- 운영에서 `① ① blind devotion` 등 5개 선택지의 번호가 두 번 표시되는 것을 확인했다.
- 원인: 별도 번호를 렌더하면서 저장된 선택지 문자열의 번호도 그대로 출력한다.
- 제안: 선택지 구조를 정규화해 표시용 번호를 한 번만 출력한다. 번호가 없는 데이터와 OX·기호 선택형을 함께 회귀 확인한다.
- 근거: `reading-review.tsx:220–257`.
- 합격 조건: 화면과 접근 가능한 이름에서 번호가 한 번만 읽힌다.

### Q04 [P1 · 실화면/코드] 해설이 열리면 문제 공간이 줄고 스크롤이 중첩된다

- 정답 확인 뒤 고정 하단에 정오·해설·과거 답·다음 버튼이 놓인다. 해설은 `max-h-32 overflow-y-auto`, 문제 영역도 별도 스크롤이다.
- 320×640에서는 하단 피드백이 큰 공간을 차지했고, 해설 내부 스크롤과 본문 스크롤을 구별해야 했다. 바깥 페이지 스크롤도 남아 있었다.
- 학생 영향: 해설의 근거 문장과 본문을 비교하기 어렵고, 어느 영역이 움직이는지 예측하기 어렵다.
- 제안: 문제·선지·해설을 하나의 주 스크롤 흐름에 두고, 하단에는 주요 버튼만 고정하는 안을 우선 검토한다. 확인 후 피드백 위치로 안내하되 원문으로 돌아올 수 있게 한다.
- 근거: `reading-review.tsx:199`, `reading-review.tsx:265–295`.
- 합격 조건: 작은 화면에서도 해설을 자연스럽게 끝까지 읽고 본문과 비교할 수 있다.

### Q05 [P2 · 실화면/코드] 오답 목록이 긴 문제 전문의 연속이다

- 최신 주차를 펼치면 문제 전문·답·해설이 연속으로 나온다. 상단에 전체 다시 풀기와 회차 다시 풀기 CTA가 반복돼 첫 문제까지의 거리도 길다.
- 학생 영향: 특정 문항을 찾기 어렵다. 해설을 읽으려다 정답을 먼저 보게 되어 스스로 회상할 기회를 놓칠 수 있다.
- 제안: 목록은 번호·유형·짧은 발문·복습 상태 위주로 요약하고, 문제를 열면 전문을 보여주는 구조를 검토한다. 복습 상세에서 정답·해설 공개 방식을 명확히 한다. 전체/회차 시작 버튼의 범위도 분명히 표시한다.
- 근거: `tabs/wrongnote-tab.tsx`, `wrong-answer-card.tsx`.
- 합격 조건: 특정 문항을 찾을 때 이전 문항의 긴 전문을 모두 지나지 않아도 된다.

### Q06 [P1 · 코드, 해당 데이터 실기 미검증] 이미지가 필요한 문제의 복습 자료 누락 가능성

- 오답 카드는 `SourceImagePreview`를 제공하지만 `ReviewQuestion`에는 원본 이미지 필드가 없고 다시 풀기에도 이미지 표시가 없다. 객관식·선지 조건만 충족하면 이미지 필수 문항도 대상이 될 수 있다.
- 학생 영향: 도표·그림 없이 답을 골라야 하는 상황이 생길 수 있다.
- 제안: 필수 이미지도 복습 화면에 전달한다. 자료가 없으면 이유를 안내하고 해당 문항을 정상적으로 풀 수 있는 문제처럼 제공하지 않는다.
- 근거: `wrong-answer-card.tsx:129`, `reading-review.tsx:18–101`.
- 합격 조건: 도표·그림·원본 필수 문항에서 풀이 자료가 모두 제공된다.

### Q07 [P2 · 코드/접근성 트리] 복습 화면의 나가기·상태·접근성

- `나가기`는 바로 닫으며 진행 상태는 로컬 컴포넌트에만 있다. 화면은 고정 div이고 별도 탐색 이력·포커스 이동 처리가 보이지 않는다.
- 운영 접근성 트리에는 복습 화면을 연 뒤에도 뒤쪽 오답 목록과 탭이 남고, 초기 포커스가 실행 버튼에 머물렀다. 선택지는 선택 여부를 `aria-pressed`/radio 상태로 전달하지 않는다.
- 제안: 진행 중 나가기의 손실을 안내하거나 세션 복구를 지원한다. 브라우저 뒤로가기, 진입·복귀 포커스, 배경 비활성화, 선택 상태 의미론을 구현한다.
- 합격 조건: 실수로 나갔다 돌아와도 정책이 명확하고, 스크린리더가 현재 문제와 선택 상태를 이해할 수 있다.

### Q08 [P2 · 코드] 연습과 기록되는 시험의 구분 부족

- 독해 다시 풀기는 로컬 연습이며 결과를 서버에 저장하지 않는다. 단어 재시험은 서버에 제출한다.
- 학생 영향: 결과가 선생님께 전달됐거나 할 일을 완료했다고 오해할 수 있다.
- 제안: 시작 또는 결과에서 ‘개인 복습’인지 ‘재시험 결과 저장’인지 짧게 알린다. 점수 퍼센트만 크게 보여주기보다 맞힌 수·남은 문항·다음 행동을 함께 제공한다.
- 근거: `reading-review.tsx`, `retake/[weekId]/page.tsx:160–190`.

## B. 단어 학습·share 앱

### S01 [P1 · 실화면/코드] 검색 결과 없음이 ‘오답 없음’으로 표시됨

- 재현: 단어장 → 오답 필터 → 일치하지 않는 검색어 입력.
- 실제로 오답이 있던 기간인데 ‘이 기간엔 틀린 단어가 없어요’가 표시됐다.
- 제안: 전체 데이터의 오답 없음과 검색/필터 결과 없음 상태를 분리한다. 바로 보이는 위치에 검색 지우기·조건 초기화를 둔다.
- 근거: `tabs/vocab-tab.tsx`의 `filteredVocabItems.length === 0` 분기.
- 합격 조건: ‘검색 결과가 없어요’로 안내하고 한 번에 검색을 해제할 수 있다.

### S02 [P2 · 실화면/코드] 단어장보다 관리용 필터 목록처럼 보인다

- 단어장 첫 화면은 전체 개수·검색·필터·상세 조건·접힌 주차 카드들이다. 단어 전체 내용은 추가 조작 후에 보인다.
- 제안: 최근 주차/이어보기 등 기본 학습 진입점을 명확히 한다. 상세 조건은 유지하되 학습보다 더 큰 시각적 비중을 갖지 않도록 한다. 검색 중에는 해당 단어를 바로 찾을 수 있게 결과 펼침 정책을 둔다.
- 근거: `tabs/vocab-tab.tsx:52`, `tabs/vocab-tab.tsx:229`.

### S03 [P2 · 코드] 완료된 단어를 통째로 흐리게 함

- `WrongVocabRow`의 재시험 통과 항목에 `opacity-60`을 적용해 본문·뜻·예문까지 흐려진다.
- 제안: 완료 배지만 약하게 구분하고 학습 내용의 대비는 유지한다. 완료 단어도 계속 복습할 수 있어야 한다.
- 근거: `wrong-answer-card.tsx:199`.

### S04 [P1 · 코드, 실기 미검증] 단어 재시험이 준비 없이 시작되고 시간이 지나면 저장됨

- 데이터 로드 직후 playing으로 전환하고 타이머 시작, 입력창 포커스, 시간 종료 시 자동 POST가 실행된다.
- 제안: 문항 수·유형·제한 시간·저장 여부를 안내한 준비 화면과 명시적 시작 버튼을 둔다. 홈/오답 CTA의 고정 ‘1분 20초’는 실제 `단어 수×10초`와 일치시킨다.
- 추가 QA: 한글 IME 조합 중 Enter가 다음 문항을 넘기는지 확인. 현재 Enter 핸들러에 composition 가드가 없다. 키보드가 올라온 실제 모바일에서 입력과 다음 버튼 가림도 확인한다.
- 근거: `retake/[weekId]/page.tsx:117–157`, `:193–205`, `:472`; `tabs/wrongnote-tab.tsx`.

### S05 [P2 · 실화면/코드] 분석 수치와 표현이 학생에게 쉽게 해석되지 않는다

- 영역은 정답률, 유형은 오답률로 방향이 달라진다. 약점 패턴에는 ‘고착·악화’ 같은 판정어가 전면에 나온다.
- 운영에서 한 카드에 ‘최근 정답률 33%’와 큰 ‘43%’가 함께 표시됐다. 서로 다른 기간의 수치인데 큰 수치의 기준은 즉시 드러나지 않는다.
- 제안: 큰 수치에 ‘기간 누적’ 등을 명시하고, 학생 행동으로 연결되는 문구를 병기한다. 예: ‘순서 문제 3개 복습하기’. 판정어는 표본 수와 함께 신중하게 제시한다.
- 근거: `tabs/analysis-tab.tsx`, `share-pattern.tsx`.

### S06 [P2 · 접근성 트리/코드] 닫힌 드로어 내용이 접근성 트리에 남음

- 일반 탭에서도 ‘오답노트 / 전체 누적 0회 / 닫기’가 접근성 트리에 노출됐다. 드로어를 transform으로 화면 밖에 이동할 뿐이다.
- 제안: 닫힌 상태는 접근성 트리·탭 이동에서 제외하고, 열린 상태의 포커스·닫기·복귀를 보장한다.
- 근거: `tag-drawer.tsx`.

## C. 관리자 설정·앱 공통 — 이번에 확인한 범위

### A01 [P2 · 실화면/코드] 설정 화면의 가용 폭과 저장 상태 안내

- 관리자 레이아웃 여백 안에 설정 페이지 여백과 카드 여백이 중첩돼 모바일 입력 폭이 좁다. 실제 화면에서 상단 설명이 줄바꿈되고 저장 버튼은 폼 아래 끝에 있었다.
- 코드상 변경 여부와 무관하게 저장 버튼이 활성화되고, 성공은 토스트로만 표시된다. 미저장 변경에 대한 안내도 없다.
- 제안: 모바일 중첩 여백을 정리하고, 변경됨/저장 중/저장 완료 상태를 구분한다. 저장 위치는 키보드와 충돌하지 않게 결정한다. 이 항목 때문에 무조건 고정 하단 UI를 추가할 필요는 없다.
- 근거: `src/app/(admin)/layout.tsx`, `src/app/(admin)/settings/page.tsx:85–127`.

### A02 [P1 · 코드, 장애 미주입] 설정 로드 실패가 빈 입력 폼처럼 보일 수 있음

- 프로필 요청은 오류를 throw하지만 페이지는 isLoading만 분기한다. 실패가 끝나면 빈 form과 활성 저장 버튼을 렌더할 수 있다.
- 학생 데이터 QA와 별개로 관리자 정보의 신뢰성 문제다. 사용자는 ‘설정이 지워졌다’고 오해할 수 있다.
- 제안: 오류·재시도 상태를 별도로 표시하고 로드 실패 중 저장을 막는다. 편집 중 재조회 데이터가 바뀔 때 현재 입력을 덮어쓰지 않도록 dirty 상태도 보호한다.
- 근거: `settings/page.tsx:24–57`, `:80`, `:123`.

### A03 [P2 · 코드] 전화번호 입력·선택 항목 안내

- 전화번호 입력은 일반 Input이고 `type=tel`/적절한 inputMode가 없다. 각 설정 필드의 선택 여부와 실제 출력 예시도 불명확하다.
- 제안: 전화 입력 키보드를 지원하고, 선택 항목·사용 위치를 짧게 안내한다. 실제 모바일 키보드 확인은 별도 필요하다.
- 근거: `settings/page.tsx:114–119`.

### A04 [P2 · 실화면/코드] 모바일 메뉴 버튼 이름과 초기 포커스

- 운영에서 메뉴 열기 버튼이 이름 없는 button으로 노출됐고, 메뉴를 연 직후 로그아웃에 포커스가 잡혔다. 닫기 이름은 영어 Close였다.
- 로컬에는 테마 선택이 추가돼 초기 포커스 결과가 달라질 수 있으므로 배포 후 재확인해야 한다.
- 제안: ‘메뉴 열기/닫기’ 이름, 현재 위치 표시, 일관된 진입 포커스를 보장한다. 로그아웃이 탐색 시작 지점이 되지 않도록 한다.
- 근거: `src/components/layout/mobile-nav.tsx` 및 운영 접근성 트리.

### A05 [P2 · 실화면] 수업 현황 헤더의 우선순위

- 모바일 헤더에 수업명·날짜·단어/숙제 수·설정·문자 발송이 함께 놓여 날짜가 여러 줄로 잘렸다.
- 제안: 수업명과 핵심 맥락을 한 그룹으로, 설정·발송을 다음 행으로 배치하는 등 좁은 폭에서의 위계를 정리한다. 학생 성적 표 자체의 모든 상호작용까지 검증한 것은 아니다.
