# 반 내부 학습기간 워크스페이스 구현

> 후속 변경: 아래 RPC 구현/적용 절차는 서버 트랜잭션 계층으로 대체되었다. 최신 적용 절차는 `2026-09-29-transaction-implementation.md`를 따른다. 이전 `separate_period_default.sql`과 전용 검증 스크립트는 미적용 상태에서 제거했다. 아래는 최초 UI 구현 당시 기록이다.

승인 시안: `class-period-workspace.html`. 기존 반 상세의 학생·달력·일정 이동·회차 추가·단어 CSV/인쇄를 유지하면서 기간 관리 UI를 분리했다.

## 변경

- 수업 목록: 운영 중 / 보관된 반 / 전체. 보관된 반 필터는 보관된 반만 표시한다. 카드 더보기는 터치와 키보드에서도 접근 가능하다. 보관/복원 전 공유 화면에 미치는 영향을 설명한다.
- 반 상세: 조회용 기간 선택 + 기간 관리. 조회는 저장 요청 없이 달력과 내보내기 범위를 변경한다. 과거 기간의 달력은 실제 수업이 있는 첫 달로 이동한다. 학생 목록은 반 전체 소속을 유지한다.
- 기간 관리: 데스크톱 우측 패널, 모바일 전체 높이 패널. 실제 기간 이름·날짜·포함 수업 횟수·공유 기본 표시. 변경 메뉴와 단순 조회를 분리한다.
- 새 기간: 이름과 첫 수업 날짜 → 변경 영향 확인. 학기/시험 구분, 수업일 빠른 선택, 날짜 검증을 유지한다.
- 기간 수정: 이름·학기·시험 구분·시작/종료일. 다른 기간 날짜를 자동 수정하지 않는다. 중복 범위와 잘못된 종료일을 안내한다.
- 공유 기본 변경: `is_current`만 변경한다. 기존 `activate` HTTP 경로는 호환을 위해 유지하되 날짜를 초기화하지 않는다. PATCH로 기본 기간을 우회 변경하는 요청은 거부한다.
- DB: `manage_class_period`는 소유 반을 잠그고 생성/수정/기본 지정/삭제를 한 트랜잭션으로 처리한다. 과거 기간을 기본으로 지정한 상태에서 새 기간을 만들 때도 날짜상 최근 기간을 종료한다. 기본 기간 삭제를 서버에서 차단한다.

## 배포 전 필수 단계

`supabase/migrations/20260929081041_separate_period_default.sql`을 개발/운영 양쪽 SQL Editor에서 적용한 뒤 앱을 배포해야 한다. 이 작업에서는 실제 개발/운영 DB에 적용하지 않았다. 함수가 없는 DB에서는 기간 조회는 가능하지만 저장 작업은 업데이트 필요 오류를 반환한다. 커밋/푸시도 아직 하지 않았다.

## 검증 방법과 범위

- 최종 `npm run check -- --maxWorkers=2 --minWorkers=1` 통과: 타입/린트 오류 0, 49개 파일·658개 테스트 통과. 기존 린트 경고만 남아 있다.
- 브라우저: 실제 페이지·컴포넌트 + 임시 API fixture로 375px 모바일/데스크톱, 라이트·다크, 조회/관리 패널, 과거 조회 시 쓰기 요청 없음, 새 기간 확인/완료, 공유 기본 확인, 보관된 반 필터와 복원 안내를 확인했다. 프로덕션 인증·실제 Supabase 연결을 통과한 브라우저 검증은 아니다.
- 유닛: 기간 조회와 변경 콜백 분리, 공유 기본 삭제 차단 메뉴, 로딩 오류 재시도, API 소유권·단일 RPC·잘못된 PATCH·삭제 충돌·생성 날짜 오류.
- 실제 PostgreSQL 엔진(PGlite, 메모리 DB): 기존 마이그레이션의 실제 테이블/인덱스/RLS와 새 함수를 실행했다. 날짜 보존, 생성 실패 롤백, 과거 기본에서 새 기간 생성, 수정, 삭제, 다른 소유자 및 익명 거부를 검증했다.
- 독립 DB 재검증: `npm install --prefix tmp/period-db-qa --no-save --package-lock=false @electric-sql/pglite` 후 `node scripts/verify-class-period-db.mjs`. 외부 DB에 연결하지 않으며 프로젝트 의존성을 바꾸지 않는다. 실행 후 임시 설치 폴더를 정리한다.

기존 기간 데이터의 중복 범위를 일괄 수정하거나 공유 접근 정책을 변경하지 않았다.
